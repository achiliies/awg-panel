# Updates

How a server running this software finds out that a newer version exists, and
how it installs one without losing anything.

There is one engine, `awg-update`, and two front ends onto it: the **Updates**
tab in the web panel, and the **Update** entry in `awg-menu`. Both drive the
same tool, so an update started from a browser and an update started over SSH
are the same operation, with the same log and the same state file — you can
start one from the panel and watch it finish from a terminal.

## What an update is

An update is the release's own installer, re-run on a server that already has
one. That is not a shortcut — it is the same upgrade path that has always been
documented, and `install.sh` reads an existing tunnel and an existing panel as
answers already given. What `awg-update` adds is everything around it: finding
out which release is newest, proving the download is the one that was published,
taking a backup first, and being somewhere the result can be read afterwards.

The steps, in order, are the phases the progress bar shows:

| Phase | What happens |
|---|---|
| `resolve` | ask which release is newest, and whether it is newer than this one |
| `preflight` | check there is room on `/` to rebuild the kernel module |
| `download` | fetch `awg-panel.sh` and `SHA256SUMS` |
| `verify` | check the bundle's sha256 against the published file, and that it unpacks |
| `backup` | write a full backup of the config tree and the database |
| `install` | run the installer |
| `confirm` | check the panel and the tunnel came back |

Nothing on the server is touched before `install`. A failure in any earlier
phase leaves the machine exactly as it was, and says so in those words.

## Checking

Only **stable** releases are ever offered. The check reads GitHub's
`/releases/latest`, which excludes drafts and pre-releases by itself, and then
refuses a release again on this side if the feed flags it as a pre-release or if
the tag carries a pre-release suffix — a hyphen, as in `v1.2.0-rc1`. A candidate
is never installed and never counted as newer.

Versions are compared the way semantic versioning says, which matters in one
place that is easy to get backwards: `1.0.0-rc1` sorts *below* `1.0.0`, not
above it. A naive comparison that pulls the digits out of a tag reads the
candidate as `1.0.0.1` and offers everybody on the release an "upgrade" to the
candidate it was cut from.

`1.2` and `1.2.0` are the same version. A tag that is not a version at all —
`nightly`, `latest` — is never newer than anything, and neither is anything at
all when the installed version cannot be read: an unreadable version on either
side means "cannot tell", and "cannot tell" is never an upgrade.

**A check that fails is not an error.** A server behind a strict egress policy
cannot reach GitHub and is not broken. The check answers with `checked: false`
and a sentence saying which of the reachable failures it was — no route, a
repository with no release yet, or GitHub rate-limiting this address — and
nothing in the panel changes state.

## Installing

Two things are proved about the download before a byte of it is executed.

**The checksum.** Every release publishes `SHA256SUMS` beside the installers,
generated by the release workflow from the files it just built. `awg-update`
downloads both, hashes the bundle and compares. A mismatch, a `SHA256SUMS` that
does not mention the bundle, or a missing `SHA256SUMS` are all the same answer:
the download is discarded and the update stops before anything is changed. This
is not a formality — the file is about to be run as root, and the checksum is
the only statement anybody made about what the bytes should be.

**The shape.** The file has to begin `#!/bin/bash` and answer `--help`, which
for a release bundle means unpacking its own payload and asking the installer
inside. A file that arrived intact and is not a bundle fails this rather than
being handed to `bash`.

Then the backup is taken — see [What is kept](#what-is-kept) — and only then is
the installer run, with `--no-ask`, so every question is answered by what is
already on the server.

The whole thing runs in its own transient systemd unit, `awg-panel-update`. That
is what makes it safe to start from a browser: the update restarts
`awg-panel-web`, so a process parented to the panel would be killed halfway
through by its own work. It is equally what makes it safe over SSH — a dropped
connection loses the log on your screen and nothing else. Come back and ask
`awg-update status`.

## From the web panel

**Settings → Updates**.

Press **Check for updates**. If there is a newer stable release you get its
version, its release notes and a button reading **Update to *X***. The
confirmation says what is about to happen; pressing it starts the update and the
page switches to a live view — the phase, a progress bar, and the tail of the
log as it is written.

Partway through, the panel restarts. The page keeps polling and every request
fails for twenty seconds or so; that is expected and the view does not treat it
as a failure. When the panel answers again the same view picks the story up from
the state file.

At the end the page offers **Reload**, and it is worth pressing: the JavaScript
in your browser is still the previous release's.

If the panel says *"This panel cannot update itself"*, the server has no
`/usr/local/bin/awg-update` — it was installed before that tool existed, or by
some other means. Run one upgrade by hand and every later one can start from the
page:

```bash
curl -fsSLO https://github.com/achiliies/awg-panel/releases/latest/download/get.sh
sudo bash get.sh
```

That is the ordinary install command, and re-running it on a server that already
has one is an upgrade: it keeps the config, the server key, the clients and the
traffic history, and it checks what it downloaded against the published
`SHA256SUMS` the same way `awg-update` would have.

## From awg-menu

`sudo awg-menu` → **Update**. The screen asks GitHub as you open it and shows
the installed version beside the newest one. What it offers depends on the
answer:

- **install** — install the release that is available. Only shown when there is
  one.
- **notes** — what changed in it.
- **rebuild** — re-run the *stored* installer at the version already installed.
  This is not an update: it rebuilds the kernel module and the tools against the
  kernel currently running, which is what a DKMS module needs after a kernel
  upgrade. It downloads nothing and works with no network at all.
- **status** — where the last update on this server got to, and its log.

Both **install** and **rebuild** close the menu and hand the terminal over. That
is deliberate rather than untidy: both replace `/usr/local/bin/awg-menu` while
bash is still holding it open, and bash reads a script in pieces as it runs it
rather than all at once. `exec` ends this process at the call, so there is no
longer anything that could read the next piece of a file that has been swapped.
Start the menu again with `awg-menu` when the run is done.

## From a shell

```bash
sudo awg-update check           # is there a newer stable release
sudo awg-update check --json    # the same answer, for a script
sudo awg-update apply           # install it, printing the log as it happens
sudo awg-update start           # start it and return immediately
sudo awg-update status          # where a running or finished update got to
sudo awg-update log -n 400      # the tail of the last one
sudo awg-update cancel          # clear a finished update's state
sudo awg-update cancel --force  # clear it even while one is running
```

Two flags:

- `--force` installs the newest release even when it is the one already there.
  For repairing an installation rather than upgrading it — including the case
  where an install stopped half way and `VERSION` is already the new one, so
  there is nothing newer to move to.
- `--skip-backup` goes ahead when the pre-update backup cannot be taken. Read
  [What is kept](#what-is-kept) before reaching for it.

`apply` starts the update in its unit and then follows the log until it ends, so
closing the terminal loses the view and not the work. `start` is what the panel
calls.

## What is kept

Everything. An upgrade keeps the server key, every client and every client key,
the addresses they are on, the obfuscation profile, the panel's port, its secret
base path, its TLS certificate, the admin account and its password, two-factor
enrolments, API tokens, quotas, expiry dates and the whole traffic history. No
client config already handed out stops working, and nobody has to be re-issued
anything.

That is a property of the installer, not a promise made here: it regenerates
none of those, because regenerating the server key alone would break every
config ever issued.

### What an upgrade will not put right

Keeping the obfuscation profile is what makes the paragraph above true, and on a
server installed from **v1.1.1** it is also what leaves a real fault in place.
That release drew `RandomTrailers` on beside header ranges a whole quarter of
the header space wide, and the two together cost about a quarter of every data
packet over roughly 470 bytes — in each direction, with nothing in any log.
Packets under that stay below the kernel's length floors and are delivered, so
ping and keepalives look perfect while throughput collapses.
[The advanced group](PANEL.md#the-advanced-group) has the mechanism.

An upgrade **finds this and says so** — on the step that keeps the
configuration, and again in the banner at the end, which is where it will still
be after a kernel build has scrolled past. It does not repair it, and that is
the deliberate part: `H1`–`H4` and the switch have to match at both ends, so
redrawing them is a config every client has to import again, and an unattended
`awg-update` that took the fleet off the air would be a worse outcome than the
bug — which at least leaves the tunnel up.

So the repair stays an operator's, at a moment they pick: **Obfuscation →
Reconfigure** in the panel, then hand out the new client configs. Clearing
`RandomTrailers` on that page is the same repair at the same reissue cost, and
keeps the wider ranges. Servers installed from any release after v1.1.1 draw the
ranges narrow and are not affected; the panel reports the pairing on any profile
that has it, however it got there.

**A tunnel MTU above 1408 is the other one**, and it reaches you the same way:
the upgrade keeps the number, and the number is now out of bounds. The panel
used to accept an MTU up to 1420, and `install.sh --mtu` took anything from
1280 to 9000, so a server sitting at 1409 or above is an ordinary one and not
an exotic one. Both bounds are 1408 now and the installer refuses what the
panel refuses, but that only stops the next install and not the one you
already have. The budget behind it counted 20 bytes for the outer IP
header, which is the IPv4 figure; the module reserves 40, because a hostname
given to `--endpoint` may resolve to an AAAA and nothing in a config records
which it will. Twenty bytes over is a datagram of up to 1520 on a 1500-byte
link, and because the outer packet carries no DF it is fragmented rather than
refused — so the tunnel stays up, small requests work, and large transfers
stall wherever the fragments do not survive.
[The per-packet budget](PANEL.md#the-per-packet-budget) has the arithmetic.

The panel does not hide it. A server over the budget carries the overrun on its
status page, and the **Server** page refuses to save until the MTU comes down —
on a field you may not have touched, which is the point: the number was already
wrong before you opened the form. The ceiling is **1408**, the budget less the
twelve bytes `S4` needs to carry a header protection nonce.

The repair is an operator's again, and at the same reissue cost. The MTU has to
match at both ends and is written into every config already handed out, so
lowering it on **Server** means handing those configs out again. Nothing is
down while you wait — a fragmenting tunnel is slow, not broken — and clients
keep running on the old number until they are reissued.

**The recommended MTU is now 1372**, and an upgrade leaves yours where it is —
this one is a better default rather than a fault, so nothing warns about it.
1400 was chosen against a 1500-byte link and fits one exactly: the largest data
packet comes to 1500 bytes with nothing to spare, which is eight bytes over the
1492 of a PPPoE line, and a client on DSL or VDSL has that packet fragmented on
every full-size transfer. 1372 is the number at which `S4` reaches its own
ceiling of 40 before the budget's, so the largest packet is 1492 whatever the
profile draws, and it crosses those links whole. It costs about 1.5% of
throughput, and it buys `S4` its full 12–40 band back — at 1400 the budget left
room for only 12–20, and the *DPI-resistant* profile had no room to vary at
all. Moving it costs a client reissue like any other MTU change, so it is worth
doing when you next hand configs out rather than on its own.

On top of it, **a full backup is taken before anything is replaced**. It goes to
`/var/lib/awg-panel/backups/awg-backup-<date>-<time>.tar.gz`, it is the same
archive **Settings → Backup** produces, and it is written through the panel's own
backup engine — which folds the kernel's live traffic counters in first,
checkpoints the SQLite write-ahead log back into the database so that the
archive, which deliberately carries no `-wal`, is not missing the last few
minutes of it, and reads the config tree under the lock the panel writes it
with. A copy taken any other way can be a database caught mid-transaction, or a
`-wal` beside a database it does not belong to, which is exactly the backup
nobody finds out about until they need it. (The collector is stopped for a
*restore*, which replaces both files underneath it; a backup only reads them.)

The path is in the state file, on the panel's progress card and in the log. The
last three are kept and older ones are deleted, so this directory cannot grow
without bound.

**An update that cannot take a backup stops.** The archive is the whole of what
protects your data through a release that turns out to be bad, and proceeding
uninsured is not a decision this tool makes on your behalf. `--skip-backup` is
there for the operator who has one already, or who has decided.

What is deliberately **not** offered is a rollback of the code. An update
rebuilds a kernel module and re-registers it with DKMS, and there is no honest
way for a shell script that has just replaced itself to put that back. The data
is what cannot be rebuilt; the code can be reinstalled from any release, and
[the next section](#when-it-goes-wrong) says how.

## The kernel module and reboots

Everything else an update installs is a file put where the old one was. The
kernel module is not: `amneziawg` is compiled against the exact kernel it will
run inside, so it has to exist, separately, for every kernel this machine ever
boots. An update is only one of the moments that matters — the other is any
kernel upgrade, which arrives on its own schedule from `apt` and takes effect at
a reboot nobody associates with the VPN.

**The chain that keeps it working** runs without this project being involved
after the first step:

1. The installer registers the module with DKMS. The source is copied to
   `/usr/src/amneziawg-<version>/`, an entry is written under `/var/lib/dkms/`,
   and the `dkms.conf` that came with the source carries `AUTOINSTALL="yes"` —
   which is the module saying "rebuild me for every new kernel".
2. The installer also puts the **kernel headers meta package** on the machine —
   `linux-headers-generic` on a stock Ubuntu box, `linux-headers-aws` on one
   booting the AWS kernel, Debian's `linux-headers-cloud-amd64` on a cloud
   image. It is chosen from the flavour of the running kernel, and its whole job
   is to keep headers arriving in the future: when `apt` installs
   `linux-image-6.8.0-140-generic`, `linux-headers-6.8.0-140-generic` comes down
   in the same transaction.
3. Still inside that same `apt` run, `dpkg` executes every file in
   `/etc/kernel/postinst.d/`, passing the new kernel's version. This is a Debian
   and Ubuntu convention, not something configured anywhere: the directory is
   the interface, and the `dkms` package ships a script into it.
4. That script runs `dkms autoinstall -k <new kernel>`. DKMS looks for
   `/lib/modules/<new kernel>/build` — which is what the headers package
   provides — compiles `amneziawg` against it, installs the result to
   `/lib/modules/<new kernel>/updates/dkms/amneziawg.ko` and runs `depmod`.
5. The module therefore exists **before the reboot**, not after it. At boot,
   `awg-quick`'s `ip link add ... type amneziawg` autoloads it by module alias,
   and the tunnel comes up like any other time.

Step 2 is the one that is easy to leave out and impossible to notice missing. A
machine carrying only the exact headers for the kernel it was installed on
satisfies every other step: DKMS is registered, the hook fires, `autoinstall`
runs — and finds no `build` tree for the new kernel, gives up, and writes a line
into a log nobody reads. Nothing fails, nothing is said, and the module for the
kernel about to be booted is simply never made.

**The kernel you have not booted yet** is the second half of the same problem,
and DKMS cannot cover it at all. The hook above fires when a kernel is
*installed*, so it covers every kernel that arrives after `amneziawg` was
registered and no kernel that was already sitting on the disk when it was — and
a kernel already sitting on the disk is what unattended upgrades leave on every
box nobody has restarted since. An install or an update on such a machine builds
for `uname -r`, reports a working tunnel, and the reboot that follows lands
somewhere with no module at all.

So the installer works out the newest kernel image in `/boot`, and where that is
not the one running, fetches its headers and builds for it too. Failing to do so
is not fatal — what was asked for is installed and running — but it says so, and
the closing summary carries it in place of the usual line about surviving kernel
upgrades:

```
  module   kernel-space - nothing built for 6.8.0-140-generic, the kernel
           this machine boots next; reboot into it and run install.sh again
```

**The boot where the module is compiled while the machine comes up** is the last
case. It happens when a kernel gets booted that DKMS never got ahead of, and
`dkms.service` rebuilds it during startup, which takes minutes. `awg-quick@awg0`
is wanted by the same target and would otherwise start inside that window, fail
on a device that cannot exist yet, and stay `failed` for the rest of the uptime
while the module quietly appears a minute later. The installer writes a drop-in
so it waits instead:

```
/etc/systemd/system/awg-quick@awg0.service.d/10-dkms.conf
    [Unit]
    After=dkms.service
```

**Checking any of this** takes three commands. The first says which kernels have
a module, the second says which one is running, the third says what the kernel
actually loaded:

```bash
dkms status
ls -1 /lib/modules/*/updates/dkms/amneziawg.ko; uname -r
cat /sys/module/amneziawg/version
```

A `.ko` under a version that is not `uname -r`, and nothing in `/sys`, is the
failure this whole section is about. The panel says the same thing in words: the
**About** page reads *Not available* when no module file exists for the running
kernel and *Not loaded* when the kernel has not got it, and the server status
carries a warning naming `modprobe` and, if that fails, the installer.

**When it genuinely cannot survive**, the causes are short and none of them are
silent once you know where to look:

- *The build fails against a new kernel.* Out-of-tree modules track kernel
  internals, and a new release can change one. The compiler's own output is kept
  at `/var/lib/dkms/amneziawg/<version>/build/make.log`. Nothing an installer can
  do fixes this; it needs a newer module release, which is what an update brings.
- *Secure Boot is on and the module is unsigned.* It builds, installs, and the
  kernel refuses to load it. `mokutil --sb-state` says whether that applies, and
  the key has to be enrolled with `mokutil --import` before a DKMS module of any
  kind will load.
- *The headers package really has no candidate* — a kernel from outside the
  distribution's archive, or a mirror that has not published them yet. `apt-get
  install linux-headers-$(uname -r)` says so directly.

Recovery, in every one of those cases where the cause has been dealt with, is
the same three lines. Nothing is regenerated and no client is affected:

```bash
sudo dkms autoinstall -k "$(uname -r)"
sudo modprobe amneziawg
sudo systemctl reset-failed awg-quick@awg0 && sudo systemctl start awg-quick@awg0
```

`reset-failed` is there because a unit that failed at boot stays failed, and a
plain `start` against one whose start limit has been counted will not run.
Where `dkms status` lists nothing at all — an uninstall took the registration
with it — re-run the installer instead, which rebuilds and re-registers from
source.

## When it goes wrong

Start here:

```bash
sudo awg-update status
sudo awg-update log -n 400
```

`status` reports one of `idle`, `running`, `succeeded` or `failed`, the versions
it was moving between, and the path of the backup it took.

**It failed before `install`.** Nothing on the server was changed. The reason is
a whole sentence — no route to GitHub, a checksum that did not match, not enough
disk. Fix that and start it again.

**It failed during `install`.** The installer says where it stopped, in the log.
The tunnel is put back by the installer's own trap if the module rebuild is what
failed. Your configuration and the backup are untouched; the usual next step is
to fix whatever the installer named (most often a missing kernel header package
or a full disk) and run `sudo awg-update apply --force`.

**It says the panel or the tunnel did not come back.** The new code is installed
and the data is intact; something did not start.

```bash
sudo awg-panel status
journalctl -u awg-panel-web -n 50
sudo awg-quick up awg0
```

**The tunnel is gone after a reboot, and it worked before.** This is almost
always the kernel module missing for the kernel that was booted, rather than
anything an update did. `systemctl status awg-quick@awg0` reporting `Cannot find
device awg0` is the same sentence whether the config is wrong or the module is
absent, so check the module first — [the section
above](#the-kernel-module-and-reboots) has the three commands and the recovery.

**You want the previous version back.** Install it by hand — every release stays
downloadable — and then restore the pre-update backup if the newer version
migrated the database:

```bash
curl -fsSL https://github.com/achiliies/awg-panel/releases/latest/download/get.sh \
  | sudo env AWG_PANEL_VERSION=vX.Y.Z bash
```

`AWG_PANEL_VERSION` names the release to take, so the bundle and the
`SHA256SUMS` it is checked against both come from that tag rather than from
whatever is newest.

Then **Settings → Backup → Restore** with the archive from
`/var/lib/awg-panel/backups/`, or `POST api/v1/restore`. Restoring is the
supported way back and it replaces the config tree and the database wholesale,
so use the archive from immediately before the update rather than an older one.

**An update seems stuck.** It is not, usually — building the kernel module takes
several minutes on a small VPS and prints nothing for a lot of it. `awg-update
log` shows whether lines are still arriving. A worker that has genuinely died is
noticed: the status endpoint checks the transient unit and reports `failed`
rather than spinning forever.

**An update refuses to start, saying one is already running.** If you are sure
there is not:

```bash
systemctl status awg-panel-update
sudo awg-update cancel
```

`cancel` asks the lock rather than the state file, so it clears a run that
ended without saying so — a worker killed by the OOM killer or lost to a hard
reset never reaches its own exit trap, and the file it leaves behind says
`running` with a pid in it. That pid belongs to something else after the next
reboot, which is why the state file also carries the boot it was written under:
a `running` state from a previous boot is read as a failure by both the tool and
the panel, whatever the pid says. `cancel --force` clears it regardless, for the
case where an update genuinely is holding the lock and you have decided anyway.

## Configuration

Both settings live in `/etc/awg-panel.env`, which is where the panel, the
collector and `awg-update` all read their configuration.

| Variable | Default | What it does |
|---|---|---|
| `AWG_PANEL_UPDATE_REPO` | `achiliies/awg-panel` | the GitHub repository releases are read from |
| `AWG_PANEL_UPDATE_URL` | unset | a whole feed URL, which overrides the repository |

The installer writes the first one on a first install and leaves it alone on
every upgrade, so an operator who has changed it keeps their answer.

**To turn the check off entirely**, set `AWG_PANEL_UPDATE_REPO` to something
that is not a repository — `AWG_PANEL_UPDATE_REPO=none`. The panel then says
there is no release source configured, and offers nothing. Restart the panel
afterwards (`sudo awg-panel restart`) so the web service picks the file up.

`AWG_PANEL_UPDATE_URL` must be `https://`. A plaintext URL is ignored and the
repository is used instead: the bytes this eventually reaches are executed as
root, and the address they come from is not something to take over cleartext.

## Forks and mirrors

**A fork** publishing its own releases sets `AWG_PANEL_UPDATE_REPO` to its own
`owner/repo` — or, better, changes `DEFAULT_REPO` in `panel/awg/release.py`,
which is the single place that string exists in the tree and the value
`install-panel.sh` writes into new env files. The releases have to carry
`awg-panel.sh` and `SHA256SUMS` under those names; the
workflow in `.github/workflows/release.yml` produces both and asserts on them.
`get.sh`, which is how a server is installed in the first place, reads the same
`AWG_PANEL_UPDATE_REPO` — so a fork's install command carries it, or its own
`get.sh` is published from a tree where `DEFAULT_REPO` was changed.

**A mirror** — a server with no route to github.com at all — has two options.
Both are about a server that is already installed; a first install through
`get.sh` takes `AWG_PANEL_RELEASE_URL=<base>` instead and expects the mirror to
serve `<base>/latest/download/<asset>`, which is the layout GitHub's own
releases URL has.
Point `AWG_PANEL_UPDATE_URL` at a mirror of the release JSON over HTTPS, or drop
the release description on the machine itself and add `AWG_UPDATE_FEED=<path>` to
`/etc/awg-panel.env`. It belongs in that file rather than in a shell: the update
runs in its own systemd unit, which inherits nothing from the terminal that
started it, and reads its configuration from there like everything else.

With a feed file, the asset URLs inside it may be `file://` paths, so a release
copied onto the box by hand installs through exactly the same checksum and
backup steps as one downloaded. The file is GitHub's own release shape:

```json
{
  "tag_name": "v1.1.0",
  "html_url": "https://example.com/releases/v1.1.0",
  "body": "what changed",
  "published_at": "2026-08-19T00:00:00Z",
  "draft": false,
  "prerelease": false,
  "assets": [
    {"name": "awg-panel.sh",
     "browser_download_url": "file:///srv/mirror/awg-panel.sh"},
    {"name": "SHA256SUMS",
     "browser_download_url": "file:///srv/mirror/SHA256SUMS"}
  ]
}
```

A feed answering with a *list* is read as `/releases` rather than
`/releases/latest`, and the newest publishable entry is picked out of it, so a
URL pointing at either shape works.

## Cutting a release

Updates only appear on servers once a release exists to appear from. Tag it, and
`.github/workflows/release.yml` does the rest:

```bash
git tag v1.1.0
git push origin v1.1.0
```

The workflow builds the UI, fetches every Python wheel and the pinned upstream
sources, packs both single-file installers, writes `SHA256SUMS`, smoke-tests all
of it, and publishes. It stamps `panel/VERSION` from the tag, which is what every
installed server compares itself against — so the version an update moves *to* is
the tag, with its leading `v` dropped.

**A hyphen in the tag makes it a pre-release.** `v1.1.0-rc1` is published,
marked `prerelease: true`, does not move `/releases/latest`, and is never
offered to a server. That is how to get a build in front of testers without
every installation being told to take it.

Two properties the workflow asserts on, because both are silent failures that
would only show up on other people's machines: that each bundle carries
`bin/awg-update` and `panel/awg/release.py` — a release missing either ends the
update chain for everyone who installs it — and that the published files are
named exactly what `panel/awg/release.py` asks for.

## How it is put together

Five pieces.

**`panel/awg/release.py`** decides what "newer" means and what a release is. It
imports nothing outside the standard library and nothing from Django, which is
why both front ends can use it: the panel imports `check()`, and `awg-update`
runs the file as a script for the same answer in JSON. A second implementation
in bash would be a second set of rules for what counts as newer, and the two
would disagree on the day it mattered.

**`bin/awg-update`** does the work: resolve, download, verify, back up, install,
confirm. It writes one small JSON object to
`/var/lib/awg-panel/update/state.json`, replaced atomically at every transition,
and its whole output to `/var/lib/awg-panel/update/log`. A `flock` on that
directory is what stops two updates at once.

**`apps/panel/update.py`** is the panel's side, and it only ever reads that state
file and starts that tool. Performing an update is not something a web request
can do — it restarts the service handling the request — so this does not try.

**The API** is three routes. `POST update/check` asks GitHub. `GET update/status`
reads the state file and is open to an API token, because watching a deployment
is a fair thing for the script that started it. `POST update/apply` starts one
and is closed to tokens, for a reason no other route on that list shares: it
replaces every line of code on the server from a release fetched over the
internet, so a leaked token that could press it would be choosing which software
the box runs next. That is a decision for a person at the login form.

**The tests** are `tests/update.sh`, `tests/get.sh` and
`panel/tests/test_api_update.py`. Between
them they cover the version ordering including every pre-release case, the
refusals — bad checksum, absent checksum, a download that is not an installer, a
backup that could not be taken, a second update while one is running — and the
endpoints' permissions. `tests/get.sh` asks the same questions of the install
command, which reaches the internet and runs what comes back in exactly the same
way, and adds the one only a piped script has to answer: that every prefix of it
does nothing, because a connection cut mid-download is how `curl | bash` fails.
What they deliberately do not do is let a run reach
`bash <the bundle>`: a test that got that far would be a test that reinstalls the
machine running it.
